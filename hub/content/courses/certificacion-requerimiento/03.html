• Teoría:

Pruebas Funcionales (qué hace el sistema)

Los tipos son:

Pruebas de regresión

  • Definición: se ejecutan para verificar que nuevas funcionalidades, correcciones o cambios en el sistema no afecten negativamente las funciones ya existentes.
  • Características:
    • Se aplican después de cada modificación del software.
    • Suelen automatizarse para reducir tiempo y esfuerzo.
    • Garantizan estabilidad y continuidad del sistema.
  • Ejemplo: tras añadir un nuevo módulo de pagos, se ejecutan pruebas de regresión para confirmar que el login, el carrito y la facturación siguen funcionando correctamente.

Pruebas de humo (smoke testing)

  • Definición: son pruebas rápidas y básicas que validan si las funciones críticas del sistema están operativas después de un despliegue o integración.
  • Características:
    • Se enfocan en los flujos principales del sistema.
    • Actúan como un “filtro inicial” antes de pruebas más profundas.
    • Si fallan, se detiene el ciclo de pruebas para evitar pérdida de tiempo.
  • Ejemplo: comprobar que el sistema inicia sesión, carga la página principal y permite realizar una transacción básica tras una nueva versión.

Pruebas exploratorias

  • Definición: se realizan sin un guion predefinido, permitiendo al tester explorar libremente la aplicación para descubrir comportamientos inesperados.
  • Características:
    • Se basan en la experiencia e intuición del tester.
    • Útiles para detectar defectos que no están documentados en los casos de prueba.
    • Complementan las pruebas estructuradas.
  • Ejemplo: un tester intenta cerrar sesión en medio de un proceso de compra para observar cómo responde el sistema.

Pruebas de aceptación del usuario (UAT – User Acceptance Testing)

  • Definición: son pruebas realizadas por el cliente o usuario final para confirmar que el sistema cumple con los requerimientos del negocio.
  • Características:
    • Validan la conformidad del software frente a criterios de aceptación definidos.
    • Son la última etapa antes de la puesta en producción.
    • Aseguran que el producto es útil y satisfactorio para el usuario.
  • Ejemplo: un banco permite a empleados de prueba validar que el sistema de transferencias cumple con las reglas de negocio y es fácil de usar.

Pruebas No Funcionales (cómo lo hace el sistema)

Los tipos son:

Pruebas de Rendimiento (Performance Testing)

  • Definición: evalúan la rapidez, estabilidad y eficiencia del sistema bajo diferentes condiciones de uso.
  • Objetivo: garantizar que el software responda dentro de tiempos aceptables y mantenga estabilidad.
  • Ejemplo: medir el tiempo de respuesta de una API con 1,000 solicitudes concurrentes.

Pruebas de Carga (Load Testing)

  • Definición: simulan un número creciente de usuarios o transacciones para validar la capacidad del sistema.
  • Objetivo: comprobar que el sistema soporta la carga esperada en condiciones normales.
  • Ejemplo: validar que un portal de e-commerce soporte 10,000 usuarios durante una campaña de descuentos.

Pruebas de Estrés (Stress Testing)

  • Definición: llevan el sistema más allá de su capacidad máxima para identificar puntos de falla.
  • Objetivo: evaluar la resistencia y recuperación del sistema en condiciones extremas.
  • Ejemplo: incrementar usuarios hasta que el servidor colapse y analizar el tiempo de recuperación.

Pruebas de Escalabilidad (Scalability Testing)

  • Definición: verifican si el sistema puede crecer en recursos (hardware, instancias en la nube) sin perder rendimiento.
  • Objetivo: comprobar que la arquitectura soporta expansión y balanceo de carga.
  • Ejemplo: añadir nodos a un clúster y validar que el sistema distribuya correctamente las solicitudes.

Pruebas de Usabilidad (Usability Testing)

  • Definición: evalúan la facilidad de uso, accesibilidad y experiencia del usuario.
  • Objetivo: asegurar que el sistema sea intuitivo y accesible para todos los perfiles.
  • Ejemplo: verificar que un formulario pueda completarse con teclado y que cumpla con normas WCAG.

Pruebas de Seguridad (Security Testing)

  • Definición: buscan vulnerabilidades que puedan ser explotadas por atacantes.
  • Objetivo: garantizar la protección de datos y la resistencia frente a ataques.
  • Ejemplo: probar un login contra ataques de SQL Injection y XSS.

Pruebas de Fiabilidad y Resiliencia (Reliability Testing)

  • Definición: evalúan la capacidad del sistema para mantener un comportamiento estable y recuperarse de fallos.
  • Objetivo: asegurar continuidad operativa y mínima pérdida de datos.
  • Ejemplo: simular caída de red y validar que el sistema se recupere sin corrupción de información.

Pruebas de Compatibilidad (Compatibility Testing)

  • Definición: validan que el software funcione correctamente en distintos dispositivos, sistemas operativos y navegadores.
  • Objetivo: garantizar una experiencia uniforme en entornos diversos.
  • Ejemplo: comprobar que una aplicación web se visualice igual en Chrome, Safari y Firefox.

Pruebas de Mantenibilidad (Maintainability Testing)

  • Definición: evalúan la facilidad con la que el software puede ser corregido, actualizado o extendido.
  • Objetivo: asegurar que el sistema sea sostenible a largo plazo.
  • Ejemplo: medir el tiempo requerido para modificar un módulo y validar que los cambios no afecten otras áreas.

Pruebas de Recuperación (Recovery Testing)

  • Definición: verifican la capacidad del sistema para recuperarse tras fallos graves o desastres.
  • Objetivo: garantizar que el sistema vuelva a un estado operativo sin pérdida significativa de datos.
  • Ejemplo: simular un corte eléctrico y comprobar que la base de datos se restaure desde backups.

Estrategias de Ejecución

Automatización

  • Definición: uso de herramientas y scripts para ejecutar pruebas de manera repetitiva y eficiente sin intervención manual.
  • Ventajas:
    • Reduce tiempo y esfuerzo en pruebas de regresión y repetitivas.
    • Mejora la cobertura y consistencia de resultados.
    • Se integra en pipelines CI/CD para validación continua.
  • Ejemplo: automatizar el flujo de login y compra en un e-commerce con Selenium o Cypress.

Priorización basada en riesgo

  • Definición: estrategia que asigna prioridad a pruebas según el impacto y probabilidad de fallo en cada requerimiento.
  • Beneficios:
    • Optimiza recursos al enfocarse en áreas críticas.
    • Reduce riesgos de fallos en producción.
  • Ejemplo: en una aplicación bancaria, priorizar pruebas en transferencias y seguridad de datos antes que en funciones secundarias como personalización de perfil.

Cobertura de pruebas

  • Definición: medida del grado en que los requerimientos, casos de uso o líneas de código han sido validados por pruebas.
  • Tipos de cobertura:
    • Funcional: porcentaje de requerimientos probados.
    • Código: porcentaje de líneas o ramas ejecutadas durante pruebas.
    • Escenarios de negocio: validación de flujos críticos definidos por el cliente.
  • Objetivo: asegurar que no existan áreas sin validar que puedan comprometer la certificación.

Evidencias

  • Definición: documentación y registros que respaldan la ejecución y resultados de las pruebas.
  • Tipos de evidencias:
    • Capturas de pantalla.
    • Logs de ejecución.
    • Reportes de herramientas (JMeter, Postman, TestRail).
    • Métricas de desempeño y defectos.
  • Importancia:
    • Proporcionan trazabilidad y transparencia en el proceso de certificación.
    • Facilitan auditorías internas y externas.
  • Ejemplo: un reporte que muestre que el endpoint /api/orders respondió en menos de 2 segundos en el 95% de las pruebas.
